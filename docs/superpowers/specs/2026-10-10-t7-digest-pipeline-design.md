# M2 T7 日报生成管线与 API 设计

状态：用户已在 2026-10-10 批准设计并授权实施。

## 范围与目标

复用 T4 的 `digests` 表，新增每日生成阶段以及历史读取 API。日报保存生成时的事件快照，供 T8 页面和 T9 离线阅读使用。任务不包含页面开发；页面开发后的本地体验验收规则见 D-012。

## 调度方案

采用现有 worker 循环加数据库去重：每轮检查配置时区下的当前日期与时间，达到生成时间且当天没有 `kind=daily` 的记录时生成。默认 `digest_hour: 8`、`digest_timezone: Asia/Shanghai`，均置于 `config/scoring.yml` 的 `digest` 段。

用户已选择：错过 08:00 后，在恢复后的首轮补生成当天日报，窗口截止到实际生成时刻；成功后同日不再自动生成。失败不留下成功日报，下一轮重试。08:00 前不生成；跨日之后只检查新一天，不自动追补过去多天。

另外两种实现是仅靠进程内记录跨过时刻，或新增独立定时服务。前者重启会丢状态，后者增加部署组件；数据库检查能直接处理重启和当天去重，适合当前单 worker 架构。

每轮开始检查日报，避免生成时间被本轮抓取和 AI 积压处理延后；日报失败独立记录，不阻断常规管线。生成函数接受显式日期与生成时刻，便于测试及手动重跑；同日期重跑替换 payload 和 generated_at，保留单行唯一约束。

## 事件选择与快照

日报默认选取过去 24 小时内热度最高的 10 个事件，`top_n` 可配置。先确定过去 24 小时的候选集合，再按热度排名取前 10；不是按更新时间取最近的 10 个。候选为 `changed_at` 落在 `[生成时刻 - 24h, 生成时刻]` 内、已评分且有中文摘要的事件：既包括新事件，也包括旧事件的新进展；排除未来时间和没有阅读内容的事件。

热度按 T7 任务定义采用时间衰减后的事件分数：用现有实时流的半衰期参数计算生成时刻的衰减分，降序取 top N；同分按 changed_at 降序、id 固定排序。保存原始分、衰减分、评分细项、标题、中文摘要、时间、来源文章及链接、已有观点对比。观点说法只保留属于该事件的 article_id，并重映射分歧索引，沿用 T6 的溯源规则。

payload 包含 `intro`、`window_start`、`window_end`、`timezone`、`events`；接口外层包含 `report_date`、`kind`、`generated_at`。时间以带时区 ISO 8601 保存。历史接口读取已保存的快照，事件后续变化不改写过去日报。

## 导语与错误处理

模型默认 `google/gemini-2.5-flash-lite`，可用 `UNSPUN_DIGEST_MODEL` 覆盖。输入仅为选中事件的已有标题与摘要；模型只输出 `{"intro": "一段简体中文导语"}`，不得生成事件事实或来源。验证导语为非空字符串，调用按 `purpose=digest` 进入现有 LLM 费用统计。

当天没有候选事件时保存空列表与固定中文导语，不调用 LLM。无密钥且存在候选事件时跳过并记录原因。LLM 错误或非法输出不覆盖已有日报；已取得的用量记录仍需提交，保证 D-007 记账。下一轮自动重试尚未成功的当天日报。

## API

- `GET /api/digest/latest`：按 report_date 降序读取最新 daily 日报。
- `GET /api/digest/{date}`：日期为 `YYYY-MM-DD`，读取该日 daily 日报。
- 没有对应日报返回 404，非法日期返回 422；latest 路由先注册，避免当作日期解析。
- 响应使用明确的 Pydantic schema，供 T8 对接；复用事件输出结构与溯源转换逻辑，避免出现两套事件协议。

## 验证与验收

自动测试覆盖配置校验、时区与 08:00 边界、停机恢复、同日跳过和跨日生成；覆盖 24h 窗口边界、未来时间排除、衰减排序、top N、空日报；以 fake LLM 覆盖导语、费用、非法输出、生成失败、同日替换及历史快照稳定性；API 覆盖 latest、历史、404、422。

实施后运行 ruff、格式检查、pyright 与 pytest；数据库集成测试必须在实际迁移后的本地 Postgres 上执行，不能将跳过测试当作通过。连续 7 天的生产生成时刻验收仍属于 T10，T7 交付时记录此项待验收。

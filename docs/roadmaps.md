# 开发路线图

这份路线图是交给 AI（Claude Code）执行的任务书。每个里程碑写明目标、范围、不做什么和验收标准；一个里程碑验收通过、并且我试用一段时间后，才进入下一个。需求细节以"需求文档"标签页为准。

| 里程碑 | 目标 | 核心产出 |
| --- | --- | --- |
| M0 | 工程骨架 | 仓库、CI、部署链路跑通 |
| M1 | MVP：验证聚类与评分 | 实时事件流 |
| M2 | 观点对比与日报 | 扩源、观点对比、日报、PWA |
| M3 | 可运营的精选情报与日报 | 后台、事件流排序、精选准入、实质进展、日报编排、兴趣与破圈 |
| M4 | 趋势与周期报告 | 趋势检测、周报、月报、可选飞书推送 |
| M5 | 经典库 | 批量导入、延伸阅读 |
| M6 | 扩展信息源 | X、B 站（元数据） |

2026-10-12 路线调整（用户确认产品方向）：优先完善内容选择、事件进展与日报阅读价值，扩源不以追赶其他产品的源数为目标。M2 随后由用户决定结案，M3 按下表子项目顺序交付，执行任务板见 `docs/tasks/m3.md`。每个子项目单独完成实施设计、PR 拆分与验收，不将整个 M3 作为一个大 PR。具体需求见 [精选与出版设计](superpowers/specs/2026-10-12-content-curation-design.md) 与 `docs/requirement.md`。

## M0 工程骨架

**目标**：在写任何业务功能之前，把 AI 开发所依赖的基础设施搭好。

**范围**

- 单仓库结构：流水线、API、前端、部署配置、信息源配置各有独立目录。
- 根目录的 CLAUDE.md：架构概览、目录约定、常用命令、禁止事项。
- Docker Compose：Postgres + pgvector、API、worker、前端静态托管；本地和线上共用。
- 数据库迁移框架。
- CI：格式检查、类型检查（TypeScript strict、pyright）、测试。
- 合并到主分支后自动部署到 VPS，经 Cloudflare Tunnel 暴露、Access 保护。
- 健康检查接口和结构化日志。

**不做**：任何抓取、AI 或业务页面。

**验收标准**

- 提交一个 PR，CI 全绿，合并后自动部署成功。
- 通过域名访问，先要求登录，登录后看到占位页和健康检查结果。
- 服务器没有开放任何入站端口。

## M1 MVP：验证聚类与评分

**目标**：用最薄的端到端链路，验证事件聚类和评分是否符合我的直觉。

**范围**

- 20–30 个有官方 RSS 的中英文源，写在配置文件里。
- 每 30 分钟增量抓取，按 URL 去重，抽取正文。
- 小模型生成摘要，统一输出中文（原文链接保留）。
- embedding 加增量事件聚类。
- 评分：客观信号分 + LLM 重要性分（按评分细则），暂不含个人相关分；权重做成配置。
- 实时事件流页面：按分数排序；事件卡片显示摘要、各来源原文链接、分数构成和评分理由。
- 基础运行报告：抓取失败的源、当日 LLM 花费。

**不做**：观点对比、日报周报月报、反馈、破圈区、经典库、RSSHub、X、B 站、PWA 离线。

**验收标准**

- 连续无人值守运行 7 天，没有中断。
- 日均 LLM 花费在预算内（月度折算不超过 50 美元）。
- 随机抽查 20 个事件，聚类明显错误（该合没合、不该合合了）不超过 3 个。
- 每个事件都能点到原文。
- 我连续使用 1–2 周，记录排序不合直觉的案例，作为调参和后续里程碑的输入。

验收执行记录（2026-10-09）：七天无人值守的集中验收经用户决定跳过，改由日运行报告持续观察；"连续使用并记录案例"跨入 M2 期间继续进行；其余各条的验收结果见 `docs/tasks/m1.md` 验收记录。

## M2 观点对比与日报

**范围**

- 自建 RSSHub，信息源扩到初版清单的规模（约 100 个），并为每个源加上地区和类型标签。
- 对来源足够多样的事件生成观点对比：并排展示各来源的说法，指出分歧点，每条说法可追溯到原文。
- 每天固定时间生成日报。
- 响应式布局与 PWA：可安装到手机桌面，日报可离线阅读。

**验收标准**

- 观点对比中每一条说法都附来源链接，抽查无张冠李戴。
- 日报连续 7 天按时生成。
- 手机断网状态下可打开当天日报。

M2 首轮收尾审计（2026-10-10，当日快照）：T1–T9 已完成开发/本地体验验收，T10 当时进行中。生产当时 63 源，低于原 80–100 的交付口径；观点说法与链接归属全量通过，但抽查的年份幻觉、短正文摘要扩写与分歧判断待修复复验；日报仅有当日 15:35 补生成一期，尚无连续七天按时证据；手机生产离线安装实测待用户结果。完整记录见 `docs/acceptance/m2-2026-10-10.md`。其后的结案决定及未齐证据见下文。

后续状态（2026-10-12）：#43 已合并内容质量补强并通过本地评测与页面验收（见 `docs/evaluations/README.md`）。用户随后明确决定“m2的任务已经完成了，可以结束m2，接下来进入m3”，据此关闭 M2、开启 M3。该决定不把未取得的七天按时日报、生产手机离线或内容生产复验记成通过；63 源按实际交付数量结案，源的可用性与缺口继续观察。未完证据与 NHK 稳定性转入 `docs/tasks/m3.md` 的承接清单，首轮审计快照保留原样。

## M3 可运营的精选情报与日报

**开工状态（2026-10-12）**：用户已确认结束 M2 并进入 M3，任务板见 `docs/tasks/m3.md`。标准事件集人工标注仍未完成；在首次评分、提示词或模型变更前须完成相应标注与 CI 评测。M2 尚缺的生产证据继续跟踪，不阻塞 M3-A 的历史查询交付。

后台六页、全部运行成本、周期账目/提醒及操作规则沿用 [后台设计](superpowers/specs/2026-10-12-admin-workspace-design.md) 和 D-015；事件流默认最新事件沿用 D-014。以下阶段替代原“后台查询 → 事件流排序 → 后台操作 → 兴趣与破圈”的直接衔接，在后台操作后先补齐内容能力。

| 顺序 | 子项目与交付边界 | 依赖与验收重点 |
| --- | --- | --- |
| M3-A | 后台查询与费用：六页查询范围、现有内容/运行状态、全部成本、周期账目及站内提醒 | 区间汇总与明细一致；当前状态单列；充值与调用不双计。尚无精选/进展数据的地方明确未记录，不等待未来模型完成才交付 |
| M3-B | 实时事件流排序与基础阅读：最新事件、当前热度、重要优先；已读状态与时间筛选 | 默认最新事件并记住选择；晚抓旧闻和旧事件新增转载不能重新作为新事件置顶；处理时间与报道时间分开。最新进展留给 M3-E |
| M3-C | 后台操作与任务基础：受控重跑、聚类纠正、配置 PR/临时覆盖；采集、处理、出版的独立任务调度；按源周期与失败退避 | 基于 A 的可观测性；任务幂等、重启恢复、预算控制、并发互斥及审计；慢源/处理积压不阻塞出版调度；保留现有日报选材口径，固定出版窗口在 F 落地 |
| M3-D | 精选准入与来源用途：元数据留存、轻量重复识别、事实/观点/信号用途、明确转载出处；准入及跳过理由；后台流程下钻 | 复用 C 的任务与预算；不改摘要后 embedding 的顺序，除非评测证明替代方案可行；固定样本检查误杀、遗漏与成本；内容类型/当前有效性分开，明显过期消息先低成本筛查，知识检查适用性，类型窗口在D0固定。观测缺失不等于零，不把不同域名视为独立证据 |
| M3-E | 事件进展：进展记录与证据、重复/背景/观点/实质变化区分，最新进展排序及读后有进展筛选 | 依赖 D 的证据和重复关系及 B 的阅读状态；转载不产生实质进展，纠错可产生进展；同主体不同事件不误合，未知时间明确展示 |
| M3-F | 日报编排与出版：以事件/进展选编、跨期去重、具体推荐理由、多样性覆盖、固定窗口、迟到与缺期处理、稳定快照 | 依赖 C–E；最多 10 条且不凑数；补生成不漂移窗口，不改历史快照；慢处理/失败/恢复可验证；真实阅读确认日报价值，初期多样性不冒充个性化破圈 |
| M3-G | 兴趣与破圈：点赞/不感兴趣、兴趣画像与相关分、领域归一化、约 20% 破圈轮换 | 依赖已读记录和 F 的选编；反馈只改变兴趣区，连续反馈一周可观察；实时流与日报破圈比例在候选充足时稳定在约 20%，不足时说明原因且不降低质量 |

**横跨各阶段的验收**

- 标准事件集评测在 M3 首次评分/提示词变更前接入 CI，未达标的 PR 不得合并；后续评分、提示词或模型变化均需通过评测。证据审核继续沿用 D-013，不因新增准入而绕过。
- D–F 开工前固定同一批候选的标注、基线与验收阈值，检查入选及排除内容；同时看重复、漏选、错误过滤、证据充分程度、领域/来源覆盖和成本。用户“值得读”的判断来自真实阅读反馈。
- C 的调度隔离和 F 的出版机制分别验证；F 上线后重新观察连续 7 天按目标时间出版，记录实际完成时间、迟到和材料缺失，不能沿用 M2 的旧观察结果。
- 手动付费操作默认遵守预算，额外额度按次授权；长期配置只在部署后标生效，临时覆盖可解除/到期；聚类纠正和重生成不改旧日报。
- 每个子项目完成相应迁移、后端与前端检查；页面变更提供本地预览并经用户实际体验验收后提 PR（D-012）。

**不做**：本阶段不新增 X/B 站接入，不以扩源数量验收；不发布周月报、不向外部群投递、不引入微服务。来源贡献驱动的自动调频与完整跨平台热度归一化在有真实观测后评测，不能用占位分数冒充已交付能力。

## M4 趋势与周期报告

**范围**

- M4-A 趋势与周报：依赖 M3 的事件进展、来源关系及稳定出版机制，识别持续变化和方向转折；每周一 08:00 发布上一个北京时间自然周的周报。
- M4-B 月报：每月 1 日 08:00 发布上一个北京时间自然月的报告，追踪前期事件的结果、判断修正与未解决问题。
- 周月报均回看完整事件/进展库，包括未入选日报的材料，不只压缩已选日报；区分报道升温与真实进展。
- M4-C 可选飞书推送：报告稳定后独立交付，默认关闭；明确配置目标并启用后，从已发布快照选少量条目附站内链接，按期号和目标防重并记录投递结果。保持单用户与 Access 边界。

**验收标准**

- 周报、月报按时生成，每个结论都能追溯到具体事件和原文。
- 固定窗口、跨周/月边界、迟到材料、失败恢复和历史快照可验证；固定样本含未入选日报但后来重要的事件，验证不会因日报筛选永久漏掉。
- 外部投递失败不影响站内报告；模拟失败重试不重复发送，未启用或无明确目标时不发送。真实启用与接收目标在该子项目验收时确认。

## M5 经典库

**范围**

- 按兴趣领域和破圈领域分批导入精选历史内容，之后定期增量补充。
- 事件下附"延伸阅读"，从经典库检索同主题旧文。
- 日报或周报增加"旧文精选"栏位。

**验收标准**

- 各领域都有经典内容覆盖。
- 抽查 20 个事件的延伸阅读，大部分确实相关。

## M6 扩展信息源

**范围**

- 接入 X：热点与关注的博主，先确认接入方式和费用。
- 接入 B 站：热门、排行榜和关注的 UP 主，只取元数据，作为热度信号和相关视频链接。
- 复用来源用途、热度观测与按源调度；依据覆盖空白、独有证据和观点贡献选择新增源，保持低频及破圈来源的机会，不以累计源数作为质量目标。
- 有真实观测后评测跨平台热度归一化和基于更新规律/贡献的自动调频；纯热度观测不能直接进入事实摘要，来源角色按条目校正。

**验收标准**

- 新源稳定抓取 7 天，失败会出现在运行报告中。
